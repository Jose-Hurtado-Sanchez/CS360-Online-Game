project overview and goals
- Our projects goal was based off of the idea of wanting to reinvent an older arcade game. Our game and project was based off of using ENET and SFML to create a client-server system that would eventually lead to an online multiplayer combat game. We took the approach of taking mortal combat and reinventing it to be an online game where 2 players can connect to the game where they can block, jab, cross, and move from left and right. Our goal was to make this game more modern and also is more simplistic than mortal combat but is user friendly, making it easy for coders to understand the game as well as understand the code written behind it. Our game will consist of needing a device that can be connected to the internet or wifi, perferably a laptop to produce the best results. We aimed to have a high funcitonality battle between two players. Throughout this project our goals and outcome was to be able to learn more about the client and server architecture and how they work together to produce a smooth flowing game using control flow keywords, while making sure users can have fun while playing our game. We wanted to take this approach because we believe this was the best way we can demonstrate what we have learned within the class and how we can apply it to projects and test our skills. 

description of the four (or more) themes used
- The four themes that we used and focused specifically on was concurrent programming, event-based concurrency, network programming, and network proxies. We chose these four themes because we believed that it could be best demonstrated within the game concept that we had. 
Our concurrent pogramming was when our code had to handle multiple things within the same game loop. So user input, network, and animation state are some examples where each loop had the client checking what the keyboard input was, send the packet, make sure to check for incoming ENet events, update the animation, and make sure it pops up on the screen. Our program had several ongoing activities rather than just performing one section. This represents it being concurrent because there were multiple proccesses that the game had to manage and process. Rather than having multiple subsystems we handle the events as they arrive and make sure to keep it simple and avoid a shared game state. 
For event-based concurrency it is where the program reacts to the event that is running. So for example when we created the sfml window loop this handles the window closing, how the ENet loop connects, recieves, and also disconnects. So based off of the event that is communicated the program will have a different outcome. So it is responding to both the sfml and enet network events that happen.
In network programming this is the majority of our code as it handles and is the main theme in our client- server system. The client creates the host, has an address and port, connects to the server, then builds the packet, sends that input across the network, make sure there are gamestate packets to recieve that information, and then update the local game state. Our machines and program are constantly communicated and uses the network library to ensure that it implements a real time client connecting to the server in the multiplayer game. We demonstrated this within our code in the enet packages, packetHeader, inputPacket, and handlePacket. We used a simple packet design where the client can safely tell between the different input packets and game-state packets. 
Our network proxies are not explicitely shown in our code but is between our client server system and is not well demonstrate but the idea is applied in the server as it acts as a communicater between the players and broadcasting the game state as it recieves their input. 

design decisions and trade-offs used
- The main design decisions within our project focused on building a simple and reliable multiplayer game. A single-threaded architecture where input handling, networking, and rendeering are process within one loop was implemented because it made it easier to debug and understand the code that was developed. However, as we continue along with this project our performance and quality diminished as we tried to implement more within our group. We had a client-server system where the server determines the game state and then relays that information to the client, making it update based on the data that it is given. We used an ENet based system to handle the communication between the machines. The architecture of our design makes sure to send input, handle packets, update the animation, and make sure there are distinct phases that make it easier to debug and understand the system as a whole. We did decide to use packets to help with handling and checking the outgoing packets starting with PacketHeader including the packet type and then the different functions send packets and different information to make sure that the data is correctly relayed. Then we also used gamestate packets that updates the psoitions and health. 

challenges encountered and lessons learned
- Some challenges that we encountered was mainly communication, getting the client-server system to work on both machines, and updating the animations as well as positions. The game could only be tested on the two mac systems that we had and we had to be in an environment where we were not on school wifi because we had to input the IP address of the other computer that was running the server into the client. This prevented us from meeting up more often because we had to do it at someones house where they had their own wifi router. Along with that it did not work correctly on one of our teammates systems because she was using windows so we were not able to test her code. Once the client and server were built seperately we had issues letting them connect on both ends because there were different variables used, issues with the firewall system allowing them to connect, and overall having both of the windows pop up on both computers showing us that the client and server were connected. As the game progressed and we were able to fix these errors we also had issues with updating the animations positions and allowing the hits to land on the players at the correct moment without it being too far out of range because we could not identify the positions. However, in the end we worked through all of these complications and was able to get the issues and kinks worked out. Throughout this process we learned about teamwork and learned more about ENet and sfml as a whole and they interact with each other. This process of creating a game was very rewarding in the end as we were able to accomplish many of the features we wanted to, but we also learned that it does take effort and compromise to be able to produce a functioning game and understand what we have produced. I believe that we gained a better understanding of how packets work and how they applied to our game as well as how the client-server system worked with two computers. It was a long process but helped us understand the importance of communication when we are working with code, how important it is to make sure to commit our code with comments as well as using git to our advantage, and how to learn how to use a new system effectively and efficiently.
