project overview and goals
- Our projects goal was based off of the idea of wanting to reinvent an older arcade game. Our game and project was based off of using ENET and SFML to create a client-server system that would eventually lead to an online multiplayer combat game. We took the approach of taking mortal combat and reinventing it to be an online game where 2 players can connect to the game where they can block, jab, cross, and move from left and right. Our goal was to make this game more modern and also is more simplistic than mortal combat but is user friendly, making it easy for coders to understand the game as well as understand the code written behind it. Our game will consist of needing a device that can be connected to the internet or wifi, perferably a laptop to produce the best results. We aimed to have a high funcitonality battle between two players. Throughout this project our goals and outcome was to be able to learn more about the client and server architecture and how they work together to produce a smooth flowing game using control flow keywords, while making sure users can have fun while playing our game. We wanted to take this approach because we believe this was the best way we can demonstrate what we have learned within the class and how we can apply it to projects and test our skills. 

description of the four (or more) themes used
- The four themes that we used and focused specifically on was concurrent programming, event-based concurrency, network programming, and network proxies. We chose these four themes because we believed that it could be best demonstrated within the game concept that we had. 
Our concurrent pogramming was when our code had to handle multiple things within the same game loop. So user input, network, and animation state are some examples where each loop had the client checking what the keyboard input was, send the packet, make sure to check for incoming ENet events, update the animation, and make sure it pops up on the screen. Our program had several ongoing activities rather than just performing one section. This represents it being concurrent because there were multiple proccesses that the game had to manage and process. 
For event-based concurrency it is where the program reacts to the event that is running. So for example when we created the sfml window loop this handles the window closing, how the ENet loop connects, recieves, and also disconnects. So based off of the event that is communicated the program will have a different outcome. So it is responding to both the sfml and enet network events that happen.
In network programming this is the majority of our code as it handles and is the main theme in our client- server system. The client creates the host, has an address and port, connects to the server, then builds the packet, sends that input across the network, make sure there are gamestate packets to recieve that information, and then update the local game state. Our machines and program are constantly communicated and uses the network library to ensure that it implements a real time client connecting to the server in the multiplayer game. We demonstrated this within our code in the enet packages, packetHeader, inputPacket, and handlePacket. We used a simple packet design where the client can safely tell between the different input packets and game-state packets. 
Our network proxies are not explicitely shown in our code but is between our client server system and is not well demonstrate but the idea is applied in the server as it acts as a communicater between the players and broadcasting the game state as it recieves their input.
